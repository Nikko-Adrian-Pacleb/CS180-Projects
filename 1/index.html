Project 1: Images of the Russian Empire

Colorizing the Prokudin-Gorskii photo collection

Background

Sergei Mikhailovich Prokudin-Gorskii travelled the Russian Empire in the early 1900s photographing everything he saw, three times over. For each scene he recorded three exposures onto a single glass plate through a red, a green, and a blue filter, betting that someone would eventually invent a way to put them back together. The Library of Congress digitized those plates, and this project is that "eventually": take a scanned plate, cut it into its three channels, and register them into one color photograph.

The only thing standing in the way is that the three exposures were taken seconds apart with a camera that moved between them. Stacking the raw thirds gives a badly fringed image, so the real work is finding the (x, y) translation that brings green and red into agreement with blue.

That is melons.tif, and it is a useful image to keep in mind for the rest of this page: its red channel is displaced by 178 pixels, which turns out to be enough to break the obvious algorithm entirely.

Approach

1. Splitting the plate

Each scan stacks the three exposures vertically in BGR order: blue on top, then green, then red. I take the image height, integer-divide by three, and slice out the three equal bands. The leftover one or two rows from the division are dropped, which keeps all three channels exactly the same shape so they can be compared elementwise. 

def split_image(im):
    height = im.shape[0] // 3
    b = im[:height]
    g = im[height: 2*height]
    r = im[2*height: 3*height]
    return b, g, r

Blue stays fixed as the reference; green and red each get aligned to it independently.

2. Scoring a candidate displacement

To decide whether one shift is better than another I need a single number measuring how well two channels agree. I implemented both standard metrics.

L2 / Sum of Squared Differences. Subtract the two images pixel by pixel, square, and sum. Identical images score zero, so lower is better. I skip the square root since it is monotonic and does not change which displacement wins. 

def l2(im1, im2):
    return np.sum((im1 - im2)**2)

Normalized Cross-Correlation. Mean-subtract each image, normalize each to unit length, and take the dot product, which is the cosine of the angle between the two images viewed as vectors. Higher is better, with 1.0 a perfect match. 

def ncc(im1, im2):
    a = im1 - im1.mean()
    b = im2 - im2.mean()
    return np.sum((a / np.linalg.norm(a)) * (b / np.linalg.norm(b)))

The difference matters because the three channels are not brightness-matched: a red filter and a blue filter looking at the same scene produce genuinely different intensities. Raw L2 punishes that global offset even when the alignment is perfect, while NCC's mean subtraction and normalization make it invariant to a constant brightness shift and a constant contrast scale.

3. Ignoring the borders

The scans carry thick black, white, and colored borders that are artifacts of the plate and the scanner, not the photograph. They are also high-contrast, which means they dominate both metrics and happily "align" borders to each other rather than image content. Before scoring I throw away the outer 10% on every side and compare only the interior. 

def crop_image(im, frac=0.1):
    h, w = im.shape
    dh, dw = int(h * frac), int(w * frac)
    return im[dh:h - dh, dw:w - dw]

This is also what makes np.roll safe to use for shifting. np.roll wraps pixels around from one edge to the other, which would be garbage at the margins. But the crop discards exactly that wrapped region before it reaches the metric.

4. Single-scale exhaustive search

The naive version: try every integer displacement in a window, score it, keep the best. For a window of ±15 that is 31 × 31 = 961 candidates per channel. 

def align(to_shift, ref, window=15, metric='ncc'):
    ref_c = crop_image(ref)
    best = (0, 0)
    best_score = np.inf if metric == 'l2' else -np.inf

    for dy in range(-window, window + 1):
        for dx in range(-window, window + 1):
            to_shift_c = crop_image(np.roll(to_shift, (dy, dx), axis=(0, 1)))
            score = l2(to_shift_c, ref_c) if metric == 'l2' else ncc(to_shift_c, ref_c)
            better = score < best_score if metric == 'l2' else score > best_score
            if better:
                best_score, best = score, (dy, dx)
    return best

5. Coarse-to-fine image pyramid

The key observation is that a 178-pixel displacement at full resolution is only a 178/2n pixel displacement after n halvings. So: shrink both channels until the image is small enough that a modest window covers the whole plausible range, solve it exhaustively there, then walk back up. At each step up the estimate doubles (because the image doubled) and a tiny ±2 refinement search corrects the rounding that doubling introduces. 

def align_pyramid(to_shift, ref, levels, base_window=30, refine=2, metric='ncc'):
    if levels == 0:
        return align(to_shift, ref, window=base_window, metric=metric)

    small_shift = rescale(to_shift, 0.5, anti_aliasing=True)
    small_ref   = rescale(ref,      0.5, anti_aliasing=True)
    dy, dx = align_pyramid(small_shift, small_ref, levels - 1, base_window, refine, metric)

    dy, dx = dy * 2, dx * 2                       # carry the estimate up one octave

    guess = np.roll(to_shift, (dy, dx), axis=(0, 1))
    ddy, ddx = align(guess, ref, window=refine, metric=metric)   # local correction

    return dy + ddy, dx + ddx

The recursion depth is chosen from the image itself rather than hard-coded, so the same code handles a 390-pixel JPEG (which bottoms out immediately at zero levels and degrades gracefully into the plain single-scale search) and a 3200-pixel TIFF (which gets 3 levels, bottoming out around 400 pixels): 

def pyramid_levels(im, min_size=250):
    levels = 0
    h, w = im.shape
    while min(h, w) // 2 >= min_size:
        h, w = h // 2, w // 2
        levels += 1
    return levels

anti_aliasing=True on the downsample matters more than it looks. Decimating without a low-pass filter aliases high-frequency detail into the coarse image, and since the coarse level is where the large displacement is decided, an aliased coarse level produces a confidently wrong answer that the ±2 refinements can never walk back.

Single-scale vs. multi-scale, side by side

Both approaches run the identical scoring function over the identical kind of search. The only difference is where they look: the single-scale version sweeps a ±15 window across the full-resolution channel, while the pyramid solves the same ±15 sweep on a heavily reduced copy and then refines upward. That one structural change decides whether the answer is findable at all.

Here are six plates run both ways, with NCC as the metric in both cases. Values pinned to the edge of the search window are marked.

All twelve single-scale estimates come back with a vertical offset of exactly 15, the largest value the window allows. That is not a coincidence and it is not the algorithm finding a genuine optimum. Every one of these plates has a true vertical displacement larger than 15, so the best available score always sits on the boundary, and the search reports the edge of its own box.

Church shows the damage spreading further than you might expect. Its true red offset is (−4, 58), and −4 is comfortably inside the window, yet single-scale returns −15 for that axis. The unreachable vertical error drags the best-scoring match into the corner and takes the horizontal estimate down with it. A too-small window does not just truncate the answer, it corrupts the components it could have recovered.

Melons and self_portrait fail loudly: the channels are visibly torn apart and nobody would mistake the result for a finished photograph. Church fails quietly, and that is the more dangerous case. It still reads as a plausible image, just drowned in a blue-violet cast, which is exactly the kind of failure that survives a quick glance at a contact sheet.

One row in that table is not a failure at all. Wharf's green channel sits at (−7, 15), and both methods return exactly that, because for once the true displacement fits inside the window. It is a useful control: the single-scale search is not broken, and its metric is not lying. When the answer is inside the region it examines, it finds it exactly. The pyramid's advantage is entirely about making sure the answer is inside that region.

The headline: the pyramid is faster and correct

The last row of that table is the one that matters. The pyramid is not a speed-for-accuracy trade. It beats single-scale search on both axes, running 5× faster than L2 and 9× faster than NCC while being the only configuration that aligns the large plates at all.

That sounds paradoxical until you recall what the section above showed: single-scale is not buying accuracy with its extra seconds. It spends 38 of them to return a displacement clamped to the edge of its own search window. Both metrics do it, on every TIFF in the set. So this is not a speed-versus-quality trade at all, and there is no configuration here where paying more gets you a better picture.

Why NCC costs roughly twice what L2 costs

Runs B and C are identical in every respect except the scoring function. Same single-scale search, same ±15 window, same 961 candidates, same images, so the gap between them isolates metric cost. Averaged over the eleven TIFFs it is 20.19 s vs. 36.84 s, a factor of 1.8.

Because those two batches ran in different sessions, I also re-measured both metrics on a single image back to back, timing only the two align calls so that file I/O drops out entirely. That controlled comparison puts the factor a little higher: 

melons.tif  SINGLE-SCALE ±15 ncc   G=(8,15)   R=(15,15)   [38.8s]
melons.tif  SINGLE-SCALE ±15 l2    G=(9,15)   R=(15,15)   [15.8s]   → 2.45x

Somewhere between 1.8× and 2.5×, then. I would not defend a more precise number than that on a laptop, but the direction is unambiguous and the mechanism explains it.

The reason is the number of full-resolution temporary arrays each one materializes per candidate. L2 builds two (the difference and its square) then reduces. NCC builds the two mean-subtracted arrays, then computes two norms (each a full pass), then an elementwise division per channel, then the product array, then the final sum. On a 3200 × 3700 float64 channel each of those temporaries is roughly 95 MB, so the metric's cost here is set almost entirely by memory traffic rather than by arithmetic. Every extra intermediate array is another 95 MB written and read back, 961 times over.

Worth noting that this is a pure cost with no benefit at this window size: B and C disagree only trivially (G=(9,15) vs G=(8,15) on melons) and both are wrong for the same structural reason. NCC's robustness advantage is real, but it shows up in which optimum gets found, not in whether a too-small window can reach it.

Where the time actually goes

Run A sets the floor: ~0.3 s per TIFF with no search at all is pure file read, float conversion, and JPEG write. Subtract that from every other column to get the true search cost. The pyramid's real alignment work is closer to 3.8 s than 4.1 s.

The pyramid's cost structure is what makes it cheap. Exhaustive search over a ±w window costs O(w2N) for N pixels. The pyramid pays that once at the coarsest level, where N has been divided by 43 = 64, and then only a handful of ±2 searches (25 candidates each) on the way back up. Even though the top of the pyramid operates on full-resolution arrays, 25 candidates there is nothing next to 961.

The JPEGs invert the ordering, which is a nice sanity check on that reasoning. cathedral/monastery/tobolsk are slower under the pyramid (1.4 to 1.6 s) than under single-scale (0.2 to 0.4 s), the opposite of every TIFF row. That is because pyramid_levels returns 0 for a 390-pixel image, so there is no pyramid at all. It collapses to a single-scale search with base_window=30 instead of 15, i.e. 3721 candidates instead of 961. A 3.9× ratio of candidate counts, and a measured 1.59/0.373 = 4.3× ratio of runtimes. The overhead of the pyramid machinery is only worth paying when there is actually a pyramid.

Where it fails: the Emir of Bukhara

The green channel aligns correctly at (24, 49) under both settings. Red is the problem: at the default base_window=30 it lands at (−205, 141), and the robe tears into color ghosts.

The cause is the assumption underneath raw-pixel NCC. NCC is invariant to an affine brightness change (one global scale and one global offset), and that is a good enough model for most of these plates. The Emir's robe breaks it. That saturated blue fabric is extremely bright in the blue exposure and nearly black in the red exposure, and it occupies a large fraction of the frame. No single scale-and-offset reconciles those two, so at the correct alignment the correlation is still mediocre, and a displacement that happens to line up dark regions with dark regions scores higher. The metric is not failing to find its maximum; its maximum is in the wrong place.

Note also where the error enters. It is decided at the coarsest pyramid level and then locked in. Once the coarse level commits to a wrong offset, the ±2 refinements on the way up can only nudge it by a couple of pixels. There is no mechanism to reconsider. This is the structural weakness of coarse-to-fine: it is fast precisely because it trusts the coarse estimate, and it fails exactly when that trust is misplaced.

An accidental fix, and why I am not counting it as one

Narrowing the coarsest-level search to base_window=15 produces R = (56, 104), which is in-family with the rest of the collection and gives the clean image on the right above. Same metric, same pyramid, same everything else; only the coarse window changed.

But this is not really a fix, and it is worth being precise about why. The spurious optimum is still there and still scores higher than the true one; the narrower window simply does not reach far enough to find it. I got the right answer by denying the search access to the wrong one. That works here and would fail on any image whose true displacement happens to be large, which is exactly the case the wide window exists to handle. A parameter that has to be tuned per-image is not a solution, and the assignment explicitly warns against over-tuning, so the results table above reports the honest base_window=30 failure.

The principled fix is to stop comparing brightness and start comparing structure. Edges appear in the same places in all three channels regardless of how each filter maps scene color to intensity, so running the identical search over gradient magnitude instead of raw pixels sidesteps the whole problem without touching the search at all. I did not implement that here, but it is the change I would make first.

My own selections from the Prokudin-Gorskii collection

Three more plates pulled from the Library of Congress archive and run through the same unmodified pipeline: same base_window=30, same NCC metric, no per-image tuning. All three are roughly 3740 × 3240 per channel, the same scale as the provided TIFFs, and all three took about the same four seconds.

The third one is the most demanding image I ran anywhere in this project: its red channel is displaced 185 pixels vertically, more than melons.tif's 178 and more than anything in the provided set. It is also the one most likely to expose a bad alignment, since a group portrait gives you a dozen faces and a lattice of pavilion railings to check against. Fringing that hides easily in foliage is obvious on a face. It comes out clean.

Worth noting that all three have a negative red x offset, where most of the provided plates are positive. Nothing deep; it just reflects which way the camera happened to drift between exposures. But it is a reminder that the search genuinely has to explore in both directions rather than assuming a consistent drift.

The first two also show the limit of what alignment alone can fix. Both have a bright cyan and magenta fringe along the plate edges, because the three exposures do not cover exactly the same field and no single translation makes the borders agree. Removing it would need a separate cropping step that detects where the border ends rather than trimming a fixed margin.

Summary

A single-scale exhaustive search over a ±15 window handles the low-resolution plates outright, so completely that L2, NCC, and the full pyramid all produce byte-identical files for them. On the full-size scans it fails totally, returning displacements clamped to the corner of its own search window while taking 20 to 37 seconds to do it.

Wrapping that same search in a coarse-to-fine pyramid fixes both problems at once: about four seconds per image, and correct alignment for displacements as large as 185 pixels. Timing the four configurations side by side showed that the pyramid is not a trade-off but a strict improvement, that NCC costs roughly twice L2 for reasons of memory traffic rather than arithmetic, and that the choice of metric is irrelevant when the search window cannot reach the answer.

Sixteen of the seventeen plates align cleanly: thirteen of the fourteen provided, plus all three I chose myself. The Emir of Bukhara is the one failure, for a reason that belongs to the metric rather than the search. And while narrowing the coarse window happens to produce the right answer for that image, it does so by luck rather than by addressing the cause.
